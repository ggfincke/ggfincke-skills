# Application Preparation

Prepare an accurate draft and leave the final application submission to the user. This workflow owns factual grounding, application identity, and the handoff; existing browser and document skills own their tool operations.

## Establish the target and authority

1. Identify the employer, exact requisition ID, official role URL, location, and intended application. Confirm current status on the employer's official site or ATS; do not substitute a similarly named role or a stale search snippet.
2. Identify the authorized resume, profile, tracker, and user-provided answers. Read only the relevant facts. Separate verified facts, draft phrasing, and unknown answers; a remembered fact may need current confirmation.
3. Define the allowed work: research, drafting, form entry, upload, tracker update, or another stated action. Reuse specific existing authorization; a request to inspect a role does not authorize uploading personal documents or creating an account.
4. Reuse the existing authenticated tab and saved application where practical. Use the appropriate installed Chrome/browser skill and actual host tools; do not start duplicate applications or bypass access controls when a session is unavailable.

Check the current site before advising on requirements, deadlines, eligibility, compensation, or other changing claims. Treat legal or compliance uncertainty as an unanswered field, not a reason to infer an answer.

## Ground each answer

| Field or claim | Source and behavior |
| --- | --- |
| Employment, education, projects, skills | Use the authorized resume or current user-provided evidence. Preserve dates, degree status, titles, and actual responsibilities; do not invent experience or inflate a draft. |
| Availability, duration, location, work authorization, government employment, conflicts | Use a current explicit answer where applicable to this requisition. Ask about an essential unknown; do not guess from nationality, school, another role, or an old application. |
| Demographic, disability, veteran, medical, or other sensitive questions | Use the user's explicit choice for this form. Do not infer from appearance, history, or silence, and do not assume a default such as “prefer not to say.” Honor a decision to leave an optional field unanswered. |
| Motivation and open responses | Draft from verified experience and the actual role. Label proposed wording for review; do not turn a suggested story or metric into a factual claim. |

Do not embed private answers, addresses, credentials, demographic choices, current availability dates, or role-specific claims in this reusable skill. Keep changing facts in the user's authorized sources. Reading a memory is not permission to add or update one.

## Fill and verify the draft

1. Confirm that the active form belongs to the intended employer and requisition before entering personal data. Apply the current host's consent rules to the exact document/data and recipient before upload or another transfer; do not add a new sharing destination.
2. Fill only grounded fields within the approved scope. Use native form controls and existing session state; pause at an essential unknown rather than selecting a plausible option.
3. After uploads, selects, autocomplete, or navigation, read the displayed values again. An upload success toast does not prove parsed education, dates, attachments, or answers are correct. Verify that a saved draft remains a draft.
4. Keep credentials and pairing/session links out of screenshots, reports, committed files, and trackers. Capture only the evidence needed for the handoff, with sensitive fields omitted or redacted when appropriate.
5. Reconcile the tracker only if authorized, using the exact requisition and current observed state. Record draft/prepared/submitted distinctly; do not mark submitted because all fields are filled.

If tools or site access fail, state the missing capability and preserve the existing draft. Do not claim a field was saved, a document was uploaded, or an application was submitted without observing that result. Avoid repeated retries that might create duplicates or transmit data twice.

## Human submission handoff

Leave the final **Submit, Finish, Apply, consent certification, or equivalent application-submission action** to the user. Do not invoke its API or automate around the visible button. Account creation, binding agreements, credential changes, and other separately consequential steps also follow the current host's required confirmation or handoff rules.

Return the official role/application link, exact requisition, current draft state, any unanswered fields or discrepancies, and the one next action the user can take. If a final review screen is available, leave it there without submitting. A later submission receipt can update the tracker only when actually verified and authorized.
